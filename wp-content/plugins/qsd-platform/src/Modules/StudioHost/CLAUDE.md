# Studio Host Backend Boundary

Global policy is defined by [AGENTS.md](../../../../../../AGENTS.md).

## Ownership and entry points

This module owns the QSD-side host for the independently built WEX Admin Dashboard at the fixed `/studio/` route — the route, document, asset delivery, and private storage only. It owns no WEX markup, presentation, or identity semantics. The one narrow, Owner-authorised exception to "no QSD business data" is `StudioAssetGateway`'s read-only logo-URL handoff described below — never a second business-data channel.

- `StudioHostModule.php` — the `/studio/` rewrite rule, document template, noindex/no-toolbar marking, and access gate. Reuses `Core\PlatformAccess::CAP` (the same capability `/station/` gates on); a visitor who needs to sign in is pointed at `AdminStationModule::url()` — consumed only as a public URL, never that module's templates, CSS, or UI.
- `StudioReleaseLock.php` — the QSD-owned pin for exactly one approved, immutable WEX Studio release (release id, manifest URL, expected manifest SHA-384 digest, expected `contract` string — committed here from a reviewed WEX closeout record, never from a request/option/runtime input, unless resolved dynamically as described below). `verifiedRelease()` delegates to `StudioManifestVerifier::verify()` against that one pinned manifest URL over HTTPS. A verified result is cached via a WP transient keyed to the pin's manifest URL (never a result cached before full verification). Moving the pin forward or back to a retained approved release is a one-line constant edit, never an asset copy — proven in `tests/studio-release-lock.php` by constructing the lock against two different pins. When the constructor is given no explicit `$pin` (the production path), it instead resolves the pin once through `StudioStagingPointer`, falling back to its own four constants whenever that collaborator has nothing newer to offer; an explicit `$pin` (test seam) always bypasses the pointer entirely, so every pre-existing pin-driven test is unaffected by it.
- `StudioManifestVerifier.php` — the one fetch-and-verify routine `StudioReleaseLock` and `StudioStagingPointer` both call, so a pointer-driven candidate release is held to exactly the same checks as the fixed pin before either persists or enqueues anything from it: an https/host-bearing URL, a non-200/network response, a manifest-body digest mismatch, an unexpected `contract`/`releaseId`, a missing/empty/malformed `files` digest inventory (every key `StudioAssetPath::isUrlSafeRelativePath()`-checked, every value a well-formed SRI digest), or an `entry`/`styles` path absent from that inventory all fail closed to `null`.
- `StudioStagingPointer.php` — the one allowlisted, QSD-owned fetch of WEX's published `staging-pointer.json` that lets `StudioReleaseLock` follow an Owner-approved release advance (or rollback to a release already seen) with no QSD code commit. Active only when the staging gate is active (`isStagingGateActive()`); everywhere else it is a no-op and the fixed pin is unchanged, so this class ships inert by default. The gate is `wp_get_environment_type() === 'staging'` **OR** a deployment-proven marker — never a browser URL/Host header or any request input, per the Owner's "never infer staging solely from a browser URL/Host header" directive after the original `WP_ENVIRONMENT_TYPE` confirmation gap proved unverifiable this session. The marker is a JSON file the `deploy-staging` CI job writes straight to the server over its own existing SSH deployment capability, immediately after copying files, naming the exact commit/branch it just deployed (`{deployedBy:'qsd-platform-ci', branch, sha, deployedAt}`); `isDeploymentProvenStaging()` accepts it only when every field matches exactly (right `deployedBy`/`branch`, 40-hex `sha`, ISO-8601 UTC `deployedAt`) — a server this job never deployed to, including production, never receives it, so the OR is still fail-closed by construction, not merely by Owner config. Neither signal requires a wp-config.php edit or a wp-admin session. Validates the pointer's exact key set, `schema`/`contract` strings, an integer `sequence`, an allowlisted `change`, a `releaseId` matching WEX's published naming shape, a `manifestPath` that is both URL-safe and *derived* from that same `releaseId` (never trusted as an independent value), a well-formed SRI `manifestDigest`, and — per WEX ADR 0025 — a `previous` that is `null` only at `sequence` 1 and otherwise an object of exactly `sequence`/`releaseId`/`manifestDigest` (each independently well-formed). Shape validity is never sufficient on its own: a candidate whose sequence is above the stored one is adopted only when that `previous` exactly names the currently stored sequence/releaseId/manifestDigest (`chainsFromStored()`) — proof of an unbroken approval chain from what this instance already verified. An unprovable gap (a forged pointer, or a multi-step skip this instance cannot independently verify from a single current-state fetch, since no historical pointer log is ever read) fails closed to the retained release rather than being silently bridged; this is a deliberate narrowing from treating any higher sequence as acceptable, directed by Reviewer verdict after the initial Phase 1I candidate. An equal sequence must name the exact already-stored release/digest — a different release claiming the same sequence number is an integrity violation, not an adoption. A chain-valid candidate is still never persisted on that alone: its named manifest must also pass `StudioManifestVerifier::verify()` — a chain-valid but unverifiable candidate (outage or tamper) leaves the retained last-known-good release untouched rather than stranding the active release on it. Any validation failure returns the caller's static fallback pin unchanged (or the retained last-known-good, when one exists). A durable `get_option` record (`qsd_studio_pointer_state`) of the highest accepted `sequence`/`releaseId`/`manifestDigest` — never a transient, which would not survive a cache eviction — is what every chain and replay/downgrade check above is measured against, including across a process restart. Per Owner directive (17 October 2026), the recheck interval is zero seconds: `resolvePin()` never skips this fetch-and-validate pass on a cached/recent result — every call, including two with no elapsed time at all, re-fetches and re-validates the pointer fresh; no TTL, transient, or invented debounce stands in for it. Immutable release assets keep their own, separate cache (`StudioReleaseLock::verifiedRelease()`'s transient, untouched by this directive). The durable record is itself fully re-validated on every read, not merely type-checked — exact key set, well-formed `releaseId`/`manifestDigest`, the one allowed `contract`, and a `manifestUrl` that is exactly the *derived* releases-base + `releaseId` + `/manifest.json` path, never an arbitrary stored URL trusted at face value. A record that fails that check is treated as tampered, not absent: it is never used to reset the anti-replay baseline, and the fixed pin is served until an Owner/Reviewer repairs it. `describeGate()`/`storedSequence()` expose this state read-only for `StudioStagingDiagnostic`, never consulted by `resolvePin()` itself. See `tests/studio-staging-pointer.php` for all of the above, including the no-code-commit advance proof, a legitimately skipped sequence with a proven chain, an unchained forged higher sequence, the forged-`previous`/tampered-manifest/tampered-state rejection cases, and every deployment-marker shape rejection.
- `StudioStagingDiagnostic.php` — a single, non-secret real-runtime report (environment type, deployment-proof status, gate state, durably stored sequence, selected release id, whether its manifest verified, and a human fallback reason) of exactly what `StudioStagingPointer`/`StudioReleaseLock` resolve to on the server this process runs on — the one gap CI file-presence checks, unit tests, and an old screenshot can never substitute for. Reused, never duplicated: it calls `StudioStagingPointer::describeGate()`/`resolvePin()`/`storedSequence()` and `StudioReleaseLock::staticFallback()`/`verifiedRelease()` directly. Invoked only from `app/cli/studio-staging-diagnostic.php`, which refuses any non-CLI `PHP_SAPI` immediately (so a direct web request to that path, which ships inside the plugin's rsynced tree, 404s instead of executing) and is itself run over SSH by the `deploy-staging` CI job's "Studio staging activation diagnostic" step, right after that job's "Record deployment-proven staging marker" step writes the marker above — giving Reviewer/Owner real-server activation evidence with no browser session or wp-admin access. Deliberately not a new REST diagnostic endpoint. See `tests/studio-staging-diagnostic.php` for the inactive-gate, active-gate-but-unverifiable-manifest, and marker-only-activation-with-real-advance cases, each via injected transport/environment/marker seams.
- `StudioAssetPath.php` — the one relative-path safety check (`isUrlSafeRelativePath()`: no `..`/`.` segment, no leading slash/backslash, no drive letter, no `%`) shared by `StudioManifestVerifier`'s and `StudioStagingPointer`'s remote path validation and any plugin-local path need.
- `StudioAssetGateway.php` — enqueues only what `StudioReleaseLock` already verified, only on `/studio/` for a signed-in platform manager, with an `integrity`/`crossorigin="anonymous"` attribute on every `<script>`/`<link>` tag it adds (via `script_loader_tag`/`style_loader_tag`, keyed off a handle this same gateway enqueued — never applied to an unrelated handle). The bundle is never copied into this repository; until the lock can verify a release, the route still renders with nothing enqueued, exactly like the old missing-local-manifest state. When a release is enqueued it also writes `globalThis.wexStudioHostOptions = { logoImageBinding: { source: 'profile.logo', target: 'imageUrl' }, sourceValues: { 'profile.logo': <url|null> } }` ahead of the WEX entry script (same `qsd-studio-config` inline handle `window.QSDStudioConfig` uses, so load order is guaranteed by the existing script dependency, not a second one). The URL comes from `Account\Support\AccountRepository`/`AccountMedia` — the same read `AccountController::projection()` already does for `brand.logo_url` — behind a constructor-injected resolver (`?callable $resolveLogoUrl`, test seam only; production default reads the real Account state). Before that value is written, `sanitizeLogoUrl()` re-validates it against the exact anchored shape `AccountMedia::url()` produces (`https://` + a plain host/path + `/qsd-account/<hex>.<AccountMedia::extensions()>`), falling back to `null` on anything else — including a value that is otherwise a valid URL but wrapped in surrounding characters (e.g. Markdown link syntax), which a bare `FILTER_VALIDATE_URL` check would not catch. Never any other Account field, never a mutation, never a new REST route.
- `studio-assets/` (plugin-local, no longer read at runtime) — the prior manually-copied WEX build. Retained in git history only as the rollback reference for this delivery mechanism, not a live fallback: a verification failure in `StudioReleaseLock` never falls back to it.
- `StudioStorage.php` — the host-private writable root for WEX's identity-space storage. Its location requires an explicit `QSD_STUDIO_PRIVATE_ROOT` constant the administrator sets in `wp-config.php` after confirming it is genuinely outside their document root — never inferred from `ABSPATH`'s position, which no code inside the install can safely assume (a subdirectory install or a web alias can make that assumption false). `root()` returns `''`, and every operation fails closed, until that constant is defined. `.htaccess`/`index.php` are still written as defence in depth; a failed write to either fails the whole initialization closed. First initialization is idempotent and fail-closed, and runs only from the explicit REST action below — never automatically.
- `Http/StudioStorageController.php` — the minimum authorized handshake: storage init status/action, and readback/write of one identity-space JSON blob. Every route requires `PlatformAccess::CAP`.
- `Core\Plugin` wires `StudioHostModule`, `StudioAssetGateway`, and `StudioStorageController` independently of `AdminStationModule`/`AssetLoader`.

## Boundaries

Never modify `AdminStationModule.php` or `AssetLoader.php` from here, and never reference their templates, CSS, or `window.QSDConfig` — Studio has its own document, its own `window.QSDStudioConfig`, and its own asset directory (`studio-assets/`, distinct from `dist/`). Never mint identity through `PlatformIdentifierStation`; WEX's own UI identity and QSD business identity stay separate. Never widen `StudioStorageController` into a generic path-addressable file API or a business-data route — it exposes exactly one bounded identity resource. Never auto-run `StudioStorage::initialize()` outside the explicit `POST /qsd/v1/studio/storage/init` action.

Read [Studio Host](../../../../../../docs/code-map/studio-host.md).

## Validation

From the plugin root: `npm test` (includes `tests/studio-host.php`, `tests/studio-asset-gateway.php`, `tests/studio-release-lock.php`, `tests/studio-staging-pointer.php`, `tests/studio-staging-diagnostic.php`, `tests/studio-storage.php`, `tests/studio-storage-unconfigured.php`, `tests/studio-storage-unwritable-root.php`, `tests/studio-storage-rest.php`, and `tests/studio-storage-rest-uninitialized.php`) and `npm run docs:check`. `QSD_STUDIO_PRIVATE_ROOT` must additionally be verified against the real deployed host — see the Code Map's Deployment-time verification section. A `StudioReleaseLock` pin change (promoting or rolling back the approved WEX release, by constant edit or by staging pointer) additionally needs one authenticated `/studio/` browser check before acceptance — CI/deploy success alone never proves the remote bundle actually renders. A staging deploy's `deploy-staging` CI job now also writes the deployment-proof marker and runs `StudioStagingDiagnostic` over SSH on every push, so `StudioStagingPointer`'s activation (via that marker or an Owner-set `WP_ENVIRONMENT_TYPE=staging`) and its selected release/sequence can be read straight from the Action log — still not a substitute for the authenticated `/studio/` browser check above, which proves the browser-facing render, not just server-side resolution.
