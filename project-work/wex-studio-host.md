## Builder — static trace complete; one live fact remains, not obtainable from this session (2026-10-14)

**Traced the full WEX consumer chain at the accepted SHA:** `logo-property-binding.js`'s `resolveLogoImagePropertyBinding()` returns `{}` (→ WEX falls back to its text label, exactly the "Logo" in Owner's screenshot) whenever either `logoImageBinding` fails `LogoImagePropertyBindingSchema` (QSD's shape is correct — verified against source), `sourceValues` isn't a plain object (QSD's is), **or** `sourceValues['profile.logo']` fails `LogoImageUrlSchema` — which requires a non-empty, ≤2048-char, valid URL that is additionally `https://` only. A `null` value (no logo uploaded) fails this the same way an `http://` value would — **both produce the identical visible symptom**, which is why a screenshot alone can't distinguish them, matching the Reviewer's own warning not to assume one cause.

**Narrowed the HTTPS-scheme branch of that question using real, unauthenticated evidence:** the public `GET /wp-json/` root (no login needed) reports `home`/`url` as `https://www.staging2.qldscubadive.com.au` and every URL anywhere in that response is `https://` — zero `http://` occurrences. `AccountMedia::url()` builds its URL from the same `wp_upload_dir()`/scheme-detection WordPress machinery, in the same request lifecycle (a normal front-end page load on `/studio/`, same as `/wp-json/`). This makes an HTTP-vs-HTTPS scheme mismatch on QSD's side unlikely, though not provable from outside without the actual live value.

**What's left, and why it genuinely needs a human:** whether `sourceValues['profile.logo']` is `null` (no Account Brand logo has been uploaded on this staging site yet — the correct, expected fallback, not a bug) or some other unexpected value cannot be determined from this session; it requires either reading the live JS global or checking Account → Brand in an authenticated session, and this session has no browser/login capability to do either (same gap recorded twice already). **One exact, fastest check:** signed in at `/studio/`, open DevTools Console and run `JSON.stringify(window.wexStudioHostOptions)` — paste the result back. If it shows `"profile.logo":null`, the fix is simply uploading a logo under Account → Brand in `/station/`. If it shows a URL, the exact string (scheme included) tells us precisely what's wrong. No further QSD code change is proposed until that fact is known — guessing and shipping a speculative "fix" against an unconfirmed cause is exactly what the Reviewer warned against.
